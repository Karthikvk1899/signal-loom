# Design decisions

1. **PostgreSQL transaction as the release boundary.** Lock the environment row before inspecting or changing a draft, approval or pointer. Separate environments do not share that lock. Snapshot signing occurs in the transaction; failure rolls back activation and audit. A single MVCC query reads pointer and signed activation consistently.
2. **Immutable proposals, explicit rebasing.** No PATCH endpoint for a revision. An approval is bound to exact content. Concurrent operators cannot silently mutate approved rules; a stale proposal is copied into a new proposal with current base generation.
3. **Rollback increments the generation.** SDK anti-regression and operator rollback must coexist. Reactivating old contents is a new release, never a pointer generation decrement. Only previously activated configurations are rollback targets.
4. **Local SDK evaluation.** Avoid a control-plane HTTP dependency per application request. This trades instantaneous global consistency for bounded staleness. The embedding app owns refresh scheduling, jitter, metrics, and defaults. Python SDK is included; other languages must match canonicalization and golden vectors before claiming compatibility.
5. **Asymmetric signatures.** Reader clients receive only a verification key, unlike an HMAC design that gives every verifier signing power. Key provisioning is a separate trust step. The current single-key design favors inspectability over production rotation sophistication.
6. **Purposeful technology selection.** Python/FastAPI supports validation and an inspectable SDK; React/TypeScript supplies the operator workflow; PostgreSQL provides the concurrency boundary. No Kafka, Redis or second backend language is added merely to list technologies.
7. **Explicit limitations over simulated integrations.** No mock OIDC login or pretend AWS deployment. Scoped API credentials demonstrate authorization boundaries while documenting that real user authentication and identity governance remain required.
